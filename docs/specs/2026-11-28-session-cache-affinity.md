# 세션 캐시 고정 강화 (2026-11-28)

Status: APPROVED (작성 세션 판단, 대표 결정 필요 항목은 운영 재기동 시점뿐)

## 문제

최근 7일 대화형 메인 호출 159,339회 가운데 대화 도중 캐시를 통째로 다시 쓴 호출이 약 8%(12,878건)이고, 이것이 캐시 쓰기 토큰의 77%(약 50억)다. 클라이언트가 대화 앞부분을 바꾼 경우는 18건뿐이라 원인은 계정 배정이다. 재작성 호출 N이 쓴 캐시를 N+1이 읽지 못하고 N+1이 N-1의 캐시를 그대로 읽는 유형(A, 3,784건)이 가장 뚜렷하다. N만 잠깐 다른 계정에 다녀왔다는 뜻이다.

운영본은 이미 `X-Claude-Code-Session-Id`로 세션 단위 고정을 하고 있다(2026-10-09 `59164767`). 그래도 새는 경로는 코드상 다음과 같다.

1. 집 계정이 동시 처리 한도(운영값 3)에 차 있으면 그 요청은 바로 다른 계정으로 간다. 집은 그대로라 다음 요청은 돌아온다. 유형 A와 일치한다. 2026-11-28 13시 실측으로 활성 23개 중 바로 쓸 수 있는 계정이 4개(슬롯 12개)였고, Claude 세션은 100개가 넘었다.
2. 넘어갈 때 고르는 계정은 이 세션이 최근 들렀던 계정(캐시 일부가 남은 곳)이 아니라 일반 선택 순서의 첫 계정이다.
3. 같은 세션의 메인 대화와 서브에이전트가 한 열쇠를 나눠 써서, 서브에이전트 몇 개만 동시에 돌아도 집이 찬다. 서브에이전트마다 대화가 달라 캐시도 따로라서 같은 집을 쓸 이유가 없다.
4. 대기열에서 깨어난 요청은 먼저 빈 계정을 잡는다. 집 슬롯이 비어도 대기열 앞쪽의 다른 세션이 가져간다.
5. 요청마다 어느 계정으로 갔는지 기록이 없어 사후 검증을 못 한다.

## 결과

- 고정 열쇠를 `세션 ID + 에이전트 ID`(`x-claude-code-agent-id`, 없으면 메인)로 바꾼다.
- 열쇠마다 최근 들른 계정을 최대 4개, 55분(캐시 수명 1시간보다 조금 짧게) 기억한다. 집을 못 쓰면 일반 선택 전에 이 목록에서 빈 계정을 먼저 고른다(유형 D의 부분 적중을 늘린다).
- 집(또는 최근 계정)이 "쓸 수 있지만 지금 꽉 찬" 상태이고 요청 본문이 크면(`affinityHoldMinBytes`, 기본 262,144바이트), 다른 계정으로 넘기기 전에 최대 `affinityHoldMs`(기본 10초) 그 계정 슬롯을 기다린다. 기다리는 동안 슬롯이 비면 그 계정 대기자에게 먼저 준다. 한 계정에서 기다리는 요청 수는 그 계정 한도(`maxConcurrent`)까지만 허용하고, 넘으면 지금처럼 바로 넘긴다(만성적으로 몰린 계정이 지연만 키우지 않게).
- 기다림이 끝나면 지금과 똑같이 일반 선택과 일반 대기열(`overflowQueueTimeoutMs`)로 간다.
- 요청마다 한 줄 기록: `[TeamClaude] Route s=<세션 해시 8자리> g=<에이전트 해시|main> acct=#<계정 번호> via=<home|warm|new|rehome|spill|preferred|grace> held=<ms>`. 계정 이름·메일·토큰은 적지 않는다. `routeLog: false`로 끈다.

## 제약

- 동시 처리 한도와 계정 활성 상태는 바꾸지 않는다. 기다림은 업스트림 동시 요청 수를 늘리지 않으므로 429 위험을 키우지 않는다.
- 기다림은 Anthropic 모드의 첫 계정 획득에만 쓴다. 실패 후 재시도(제외 목록이 있는 경우), `preferredAccountUuid` 복구 경로, /byok, Codex 모드, 워밍업 대상이 남은 동안은 쓰지 않는다.
- 상태 응답(`/teamclaude/status`)에 새 필드를 넣지 않는다(소비자 3곳 배선 부담).
- 외부 의존성 추가 없음.

## 범위 밖

- `maxConcurrentPerAccount` 조정, 계정 선택 순서(use-or-lose) 변경.
- 한도 임박으로 집을 옮기는 동작. 지금도 옮긴 계정이 새 집이 되므로 왕복하지 않는다(유지).
- 워밍업 대상이 있을 때 고정을 건너뛰는 동작(현재 운영에서 미측정 계정 0개라 영향 없음, 유지).

## 수용 기준

1. 같은 세션의 메인과 서브에이전트 요청은 서로 다른 열쇠를 쓴다(단위 테스트).
2. 집이 꽉 차고 다른 계정이 비었을 때, 큰 요청은 집 슬롯이 비면 집으로 간다(기다림 상한 안). 작은 요청은 바로 넘긴다(단위 테스트).
3. 기다림 상한을 넘기면 다른 계정으로 간다(단위 테스트).
4. 집을 못 쓰면 최근 들른 계정이 차가운 계정보다 먼저 선택된다(단위 테스트).
5. 한 계정 기다림 수가 한도를 넘으면 바로 넘긴다(단위 테스트).
6. 기존 전체 테스트가 통과한다.
7. 운영 반영 전후로 통째 재작성 비율(기준선: 대화형 메인 호출의 약 8%, 캐시 쓰기의 약 77%)과 429·대기 시간을 같은 방법으로 비교한다.

## 검증 방법

- `env -u TEAMCLAUDE_SESSION_SUPERVISED -u TEAMCLAUDE_CLAUDE_BIN node --test` 전체.
- 독립 적대 검토 `codex-astra-review.sh`.
- 반영 후: Route 기록의 `via` 분포, `~/.claude/projects/*/*.jsonl` 재작성 비율, 중계기 기록의 429·`No eligible capacity` 빈도.

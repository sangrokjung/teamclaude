# 세션 캐시 고정 강화 (2026-11-28)

Status: APPROVED (작성 세션 판단, 대표 결정 필요 항목은 운영 재기동 시점뿐)

## 문제

최근 7일 대화형 메인 호출 159,339회 가운데 대화 도중 캐시를 통째로 다시 쓴 호출이 약 8%(12,878건)이고, 이것이 캐시 쓰기 토큰의 77%(약 50억)다. 클라이언트가 대화 앞부분을 바꾼 경우는 18건뿐이라 원인은 계정 배정이다. 재작성 호출 N이 쓴 캐시를 N+1이 읽지 못하고 N+1이 N-1의 캐시를 그대로 읽는 유형(A, 3,784건)이 가장 뚜렷하다. N만 잠깐 다른 계정에 다녀왔다는 뜻이다.

운영본은 이미 `X-Claude-Code-Session-Id`로 세션 단위 고정을 하고 있다(2026-10-09 `59164767`). 그래도 새는 경로는 코드상 다음과 같다.

1. 집 계정이 동시 처리 한도(운영값 3)에 차 있으면 그 요청은 바로 다른 계정으로 간다. 집은 그대로라 다음 요청은 돌아온다. 유형 A와 일치한다. 2026-11-28 13시 실측으로 활성 23개 중 바로 쓸 수 있는 계정이 4개(슬롯 12개)였고, Claude 세션은 100개가 넘었다.
2. 같은 세션의 메인 대화, 서브에이전트, 다른 모델의 보조 호출이 한 열쇠(한 집)를 나눠 쓴다. 서브에이전트 몇 개나 보조 호출만 겹쳐도 메인 대화의 집이 찬다. 이들은 대화나 모델이 달라 캐시도 따로라서 같은 집을 쓸 이유가 없다.
3. 요청마다 어느 계정으로 갔는지 기록이 없어, 1번(집이 차서 넘어감)이 실제로 얼마나 되는지 잴 수 없다.

## 결과

- Anthropic 모드의 고정 열쇠를 `세션 ID + 에이전트 ID(x-claude-code-agent-id, 없으면 메인) + 요청 본문 최상위 모델`로 바꾼다. 캐시가 대화별·모델별로 따로라서 집도 그 단위로 둔다. advisor 도구 모델은 한도 판정용이라 열쇠에 쓰지 않는다. 세션 열쇠는 추론 요청(`POST /v1/messages`)에만 쓰고, count_tokens 같은 보조 호출은 연결 열쇠를 쓴다. 열쇠는 본문을 읽은 뒤 요청당 한 번만 만든다(요청 시작 때는 자리표시만 둔다). Codex 모드는 지금처럼 세션 ID만 쓴다.
- 요청마다 한 줄 기록: `[TeamClaude] Route s=<세션 해시 8자리|-> g=<에이전트 해시|main|-> acct=#<계정 번호> via=<home|new|rehome|spill|bypass|pick|preferred|grace> held=<ms>`. 세션 헤더가 없는 요청도 `s=- g=-`로 남긴다. 일반 선택이 결국 집을 고르면 `home`, 워밍업으로 고정을 건너뛰었으면 `bypass`로 적어 `spill`(집이 차서 다른 계정으로 감)이 실제 이동만 세게 한다. 사유는 그 요청을 배정한 순간에 확정한다(`acquireAccountRouted()`가 새 `{ account, via }`를 돌려준다). 계정 이름·메일·토큰은 적지 않는다. `routeLog: false`로 끈다.

## 제약

- 동시 처리 한도, 계정 활성 상태, 계정 선택 순서는 바꾸지 않는다. 업스트림 동시 요청 수도 늘지 않으므로 429 위험을 키우지 않는다.
- 상태 응답(`/teamclaude/status`)에 새 필드를 넣지 않는다(소비자 3곳 배선 부담).
- 외부 의존성 추가 없음.

## 범위 밖 (후속 과제)

독립 검토에서 같은 부위에 라운드마다 다른 경합·입력 변형이 3라운드 연속 나온 부수 장치는 `review-loop`의 "수렴하지 않는 부위는 범위에서 뺀다" 규칙에 따라 이 PR에서 뺐다. 처리 주체는 이 작업 계보의 다음 세션이고, 근거 데이터는 이 PR의 Route 기록이다.

- **집 슬롯 대기(hold).** 큰 요청이 집이 찼을 때 차가운 계정으로 넘어가기 전에 몇 초 기다리는 장치. 대기열 순서 역전, continuity 마감 초과, 대기 전환 뒤 순번 상실, 다른 모델 집으로의 배정이 차례로 지적됐다. Route 기록의 `via=spill` 비율이 재작성의 큰 몫이면, 대기 전환 없이 한 waiter가 하나의 절대 마감을 갖는 대기열 구조로 다시 설계한다.
- **캐시 계정 기억(warm).** 집을 못 쓸 때 이 열쇠의 캐시가 남은 다른 계정을 먼저 고르는 장치. 기록 시점(배정 때, 실패 응답, 캐시 사용량 0인 성공 응답, 최상위 cache_control)이 차례로 지적됐다. 다시 넣는다면 응답의 실제 cache read/write 사용량(JSON·SSE)에서만 기록한다.
- **재작성 비율 측정 스크립트.** 끝줄 개행, id·시각 없는 호출, 모델 null, 혼합 TTL, 측정 창 밖 행 같은 입력 변형이 차례로 지적됐다. 반영 전후 비교는 저장소 밖 운영 도구로 한다.
- 일반 대기열 waiter가 슬롯 배정 직전에 절대 마감을 검사하지 않는 점(기존 동작, 검토의 Pre-existing).
- 모델 fallback이 본문 모델을 바꿔도 원래 모델의 열쇠를 쓰는 점(fallback이 계속 같은 모델로 가므로 집은 일관된다).
- `maxConcurrentPerAccount` 조정, 계정 선택 순서(use-or-lose) 변경, 기존 대형 파일 분리.

## 수용 기준

1. 같은 세션의 메인과 서브에이전트 요청, 다른 모델의 요청은 서로 다른 열쇠를 쓰고, advisor 도구만 붙인 요청은 같은 열쇠를 쓴다. count_tokens는 세션 열쇠를 쓰지 않는다(테스트).
2. 집이 차면 지금처럼 바로 다른 계정으로 가고 집은 유지된다(테스트).
3. 요청마다 Route 한 줄이 남고, 대기열에서 배정된 요청도 자기 사유를 받는다. 같은 계정이면 `home`, 워밍업 우회는 `bypass`다. 기록에 원본 세션·에이전트 ID와 토큰이 없다(테스트).
4. 기존 전체 테스트가 통과한다.
5. 운영 반영 전후로 통째 재작성 비율과 429·대기 줄 수를 같은 방법으로 비교한다. 기준선(2026-11-25 13:00 ~ 11-28 13:00 KST): 메인 대화 약 8.2%, 서브에이전트 약 5.6%. 중계기 기록 하루 429 줄 3~21건, 전 계정 만석 대기 줄 하루 1.4만~5만 건.

# 세션 캐시 고정 강화 (2026-11-28)

Status: APPROVED (작성 세션 판단, 대표 결정 필요 항목은 운영 재기동 시점뿐)

## 문제

최근 7일 대화형 메인 호출 159,339회 가운데 대화 도중 캐시를 통째로 다시 쓴 호출이 약 8%(12,878건)이고, 이것이 캐시 쓰기 토큰의 77%(약 50억)다. 클라이언트가 대화 앞부분을 바꾼 경우는 18건뿐이라 원인은 계정 배정이다. 재작성 호출 N이 쓴 캐시를 N+1이 읽지 못하고 N+1이 N-1의 캐시를 그대로 읽는 유형(A, 3,784건)이 가장 뚜렷하다. N만 잠깐 다른 계정에 다녀왔다는 뜻이다.

운영본은 이미 `X-Claude-Code-Session-Id`로 세션 단위 고정을 하고 있다(2026-10-09 `59164767`). 그래도 새는 경로는 코드상 다음과 같다.

1. 집 계정이 동시 처리 한도(운영값 3)에 차 있으면 그 요청은 바로 다른 계정으로 간다. 집은 그대로라 다음 요청은 돌아온다. 유형 A와 일치한다. 2026-11-28 13시 실측으로 활성 23개 중 바로 쓸 수 있는 계정이 4개(슬롯 12개)였고, Claude 세션은 100개가 넘었다.
2. 넘어갈 때 고르는 계정은 이 세션이 최근 들렀던 계정(캐시 일부가 남은 곳)이 아니라 일반 선택 순서의 첫 계정이다.
3. 같은 세션의 메인 대화와 서브에이전트가 한 열쇠를 나눠 써서, 서브에이전트 몇 개만 동시에 돌아도 집이 찬다. 서브에이전트마다 대화가 달라 캐시도 따로라서 같은 집을 쓸 이유가 없다.
4. 요청마다 어느 계정으로 갔는지 기록이 없어, 1번(집이 차서 넘어감)이 실제로 얼마나 되는지 잴 수 없다.

## 결과

- 고정 열쇠를 `세션 ID + 에이전트 ID(x-claude-code-agent-id, 없으면 메인) + 요청 본문 최상위 모델`로 바꾼다. 캐시는 대화별·모델별로 따로라서 집도 그 단위로 둔다(advisor 도구 모델은 한도 판정용이라 열쇠에 쓰지 않는다). 세션 열쇠는 추론 요청(`POST /v1/messages`)에만 쓴다. 캐시를 만들지 않는 count_tokens 같은 보조 호출은 연결 열쇠를 쓴다. Codex 모드는 지금처럼 세션 ID만 쓴다.
- 열쇠마다 캐시를 가진 계정을 최대 4개 기억한다. 기록은 배정 때가 아니라 캐시 지점(cache_control)이 있는 추론 요청이 2xx로 받아들여진 뒤에만 남기고, 그 요청이 밝힌 캐시 수명(1시간 또는 5분)의 90%만큼 유효로 본다. 실패한 요청이나 캐시를 만들지 않는 요청은 계정을 따뜻하게 만들지 않는다. 집을 못 쓰면 일반 선택 전에 이 목록에서 빈 계정을 먼저 고른다(유형 D의 부분 적중을 늘린다). Codex 계정은 기억하지 않는다.
- 요청마다 한 줄 기록: `[TeamClaude] Route s=<세션 해시 8자리|-> g=<에이전트 해시|main|-> acct=#<계정 번호> via=<home|warm|new|rehome|spill|bypass|pick|preferred|grace> held=<ms>`. 세션 헤더가 없는 요청도 `s=- g=-`로 남긴다. 일반 선택이 결국 집을 고르면 `home`, 워밍업으로 고정을 건너뛰었으면 `bypass`로 적어 `spill`(집이 차서 다른 계정으로 감) 비율을 부풀리지 않는다. 사유는 그 요청을 배정한 순간에 확정한다(`acquireAccountRouted()`가 새 `{ account, via }`를 돌려준다). 계정 이름·메일·토큰은 적지 않는다. `routeLog: false`로 끈다.
- 측정 스크립트 `scripts/cache-rewrite-rate.py`: 같은 모델의 직전 호출과, 그 호출이 쓴 캐시 수명(1시간/5분) 안일 때만 비교해 통째 재작성 비율을 낸다. 읽기 실패·깨진 줄·id나 시각이 없는 호출·쓰는 중인 끝줄이 있으면 0이 아닌 종료 코드로 불완전한 측정을 구분한다.

## 제약

- 동시 처리 한도와 계정 활성 상태는 바꾸지 않는다. 배정 순서만 바꾸고 업스트림 동시 요청 수는 늘리지 않으므로 429 위험을 키우지 않는다.
- 상태 응답(`/teamclaude/status`)에 새 필드를 넣지 않는다(소비자 3곳 배선 부담).
- 외부 의존성 추가 없음.

## 범위 밖 (후속 과제)

- **집 슬롯 대기(hold)를 뺐다.** 큰 요청이 집이 찼을 때 차가운 계정으로 넘어가기 전에 몇 초 집 슬롯을 기다리는 장치를 넣었으나, 독립 검토 3라운드 연속 같은 장치에서 매번 다른 경합(대기열 순서 역전, continuity 마감 초과, 대기 전환 뒤 순번 상실, 다른 모델 집으로의 배정)이 나와 `review-loop` "수렴하지 않는 부위는 범위에서 뺀다"(대표 결정 2026-11-26, 0ab6784cebab)에 따라 뺐다. 이 PR은 대신 Route 기록으로 `via=spill`(집이 차서 넘어감) 비율을 잰다. 그 비율이 재작성의 큰 몫이면 대기열 자체에 "따뜻한 계정 우선" 순번을 넣는 설계(대기 전환 없이 한 waiter가 하나의 절대 마감을 갖는 구조)로 다시 다룬다. 처리 주체: 이 작업 계보의 다음 세션.
- `maxConcurrentPerAccount` 조정, 계정 선택 순서(use-or-lose) 변경.
- 한도 임박으로 집을 옮기는 동작. 지금도 옮긴 계정이 새 집이 되므로 왕복하지 않는다(유지).
- 워밍업 대상이 있을 때 고정을 건너뛰는 동작(현재 운영에서 미측정 계정 0개라 영향 없음, 유지).
- 기존 대형 파일(account-manager.js 3천여 줄, server.js 5천여 줄)의 분리.

## 수용 기준

1. 같은 세션의 메인과 서브에이전트 요청, 다른 모델의 요청은 서로 다른 열쇠를 쓴다. count_tokens는 세션 열쇠를 쓰지 않는다(테스트).
2. 집을 못 쓰면 캐시가 살아 있는 계정이 차가운 계정보다 먼저 선택되고, 수명이 지난 기억은 쓰지 않는다(테스트).
3. 캐시 기록은 캐시 지점이 있는 2xx 추론 응답에만 남고, 배정만 된 계정·Codex 계정은 기억하지 않는다(테스트).
4. 요청마다 Route 한 줄이 남고, 대기열에서 배정된 요청도 자기 사유를 받는다. 기록에 원본 세션·에이전트 ID와 토큰이 없다(테스트).
5. 측정 스크립트가 모델별 직전 호출과 비교하고, 불완전한 측정을 종료 코드로 구분한다(테스트).
6. 기존 전체 테스트가 통과한다.
7. 운영 반영 전후로 통째 재작성 비율과 429·대기 줄 수를 같은 방법으로 비교한다. 기준선(2026-11-25 13:00 ~ 11-28 13:00 KST, 측정 스크립트 종료 코드 0): 메인 대화 40,648회 중 3,331회 8.19%(캐시 쓰기의 91.7%), 서브에이전트 23,362회 중 1,298회 5.56%. 중계기 기록 하루 429 줄 3~21건, 전 계정 만석 대기 줄 하루 1.4만~5만 건.

## 되돌리기

`affinityWarmAccounts: 0`으로 캐시 계정 기억을 끄고 `routeLog: false`로 기록을 끈다(설정 변경 후 재기동). 서브에이전트 열쇠 분리까지 되돌리려면 이전 tarball 재설치 후 재기동.

# `teamclaude cloud-feed`: 크레딧 만료 전 자동 공급과 PR 분류

- Intent: docs/intents/2026-10-21-cloud-credit-feeder.md

Status: accepted
관련: `docs/specs/2026-10-18-cloud-dispatch-command.md` (PR #68)

## 목표
세션 판단 없이 launchd 주기로 일을 골라 `attemptCloudDispatch`로 보내고, 돌아온 PR을 상태별로 분류해 대표가 볼 수 있게 한다. 자동 머지는 후속 단계(별도 PR, 브랜치 `feat/cloud-feed-automerge`)로 분리한다.

## 명령
- 옵션은 정확히 `--dry-run`, `--max <숫자>`만 받고, 그 밖의 옵션·중복·값 누락은 아무것도 하지 않고 오류로 끝낸다.
- `teamclaude cloud-feed run [--dry-run] [--max N]`: 예산 계산 → 후보 수집 → 중복 제외 → N건 디스패치.
- `teamclaude cloud-feed triage [--dry-run]`: 보낸 브랜치의 PR을 찾아 상태를 분류한다(리뷰·머지는 하지 않음).
- `teamclaude cloud-feed tick`: run 뒤 triage(launchd가 부름).
- `teamclaude cloud-feed status`: 상태 파일 요약(보냄·머지·대기·건너뜀).
- 설정 `cloudFeed.enabled`가 true가 아니면 run·triage는 아무것도 하지 않는다(킬 스위치). dry-run은 꺼져 있어도 미리보기를 한다.

## 예산(속도 조절)
속도 조절은 서로 독립된 두 장부로 한다. 하나를 날짜 경계에서 초기화하면 다른 하나의 값이 사라지는 사고(10/21 round15 교차 검증에서 지적)를 피하기 위해서다.

- **하루 장부(`state.day`, 매일 초기화):** 오늘의 목표만 다룬다. 계정별로 그날 처음 관측한 잔액을 연다. 하루 목표 = 그 합 ÷ 만료까지 남은 일수(최소 1일, 만료 시각 `cloudFeed.expiresAt` 기본 2026-11-05T07:59:00Z). 오늘 실측 지출은 매번 "오늘 연 잔액 − 계정별로 마지막으로 본 잔액"을 다시 계산한다(누적 차감이 아니라 매번 opening 기준 재계산). 계정이 빠지면(잠금·만료·비활성) 그 계정의 마지막 관측값을 그대로 두어, 빠진 것 자체를 지출로 보지 않고 이미 관측한 지출도 잃지 않는다. 새로 들어온 계정은 자기 잔액만 그 날 목표에 더한다.
- **예약 장부(`state.ledger`, 날짜와 무관하게 영속):** 아직 실측에 반영되지 않은 발송 비용을 추적한다. 지금까지 보낸 전체 건수(exit 0·4, 날짜로 거르지 않음) 중 이 장부가 아직 세지 않은 만큼 `estCost`씩 새로 더하고, 계정별 "마지막으로 본 잔액"(이 장부 전용, 하루 장부와 별도) 대비 실제로 줄어든 금액만큼만 정산해 깎는다(남는 정산액은 버림). 자정이 지나도 이 장부는 리셋되지 않으므로, 자정 직전에 보낸 건의 예약이 날짜가 바뀌었다고 사라지지 않는다.
- 오늘 쓴 금액 = 하루 장부의 실측 + 예약 장부의 미정산액. 이번 실행 허용 건수 = min(`perRun`(기본 3), ceil((하루 목표 − 오늘 쓴 금액) ÷ `estCost`(기본 $3))). 0 이하면 보내지 않는다.
- 잔액은 실제 발송과 같은 기준(`isCloudEligibleAccount`: 활성, 5분 이상 유효한 OAuth 토큰)의 계정만 센다. 나머지와 크레딧이 잠긴 계정은 `excluded`(잠금을 지출로 오인하지 않음). 응답은 왔지만 크레딧 지급이 없는 계정은 $0으로 센다.
- 설정값은 시작 전에 검증한다(정수·양수·날짜·소유자 이름 등). 잘못된 값이면 아무것도 계획하지 않고 오류로 끝난다.
- 대상 계정 중 하나라도 크레딧 조회가 실패하면 그 회차는 보내지 않고 두 장부 모두 갱신하지 않는다(부분합을 잔액으로 쓰면 목표가 왜곡된다).

## 후보(대표 결정 4종, 번갈아 섞음)
1. 이슈: 보낼 수 있는 저장소(아래)의 열린 이슈 중 작성자가 OWNER·MEMBER·COLLABORATOR인 것(자동 머지까지 이어지므로 외부인 글은 쓰지 않음). `no-cloud` 라벨 제외. 키 `issue:<repo>#<n>`.
2. TDL: `os_tasks` status=todo이고 프로젝트에 `github_repo`가 있는 것(읽기 전용 조회). 키 `tdl:<id>`.
3. 리뷰: 열린 PR 중 같은 저장소 브랜치(포크 아님)이고 작성자가 쓰기 권한자인 것(디스패치 브랜치·봇·초안 제외). 클라우드는 목록에서 본 정확한 head 커밋(SHA)에서 시작해 그 PR 브랜치를 대상으로 수정 PR을 연다(`prTarget`). 키 `review:<repo>#<n>@<head 전체 SHA>`이고, head가 바뀌면 새 키다.
4. 정기 개선: 로컬 클론 저장소마다 주차별로 테스트 보강·보안 점검·리팩터·문서 중 하나. 키 `improve:<repo>:<주>`.
- 네 소스를 한 줄로 섞을 때 매번 같은 소스가 맨 앞을 차지하지 않도록, 실행마다 맨 앞 소스를 한 칸씩 돌린다(`state.rotation`, 소스 개수로 나눈 나머지). 그래서 이슈가 계속 새로 들어와도 TDL·리뷰·개선 작업이 영영 밀리지 않는다.
- 저장소는 로컬 클론(설정 `roots`, 기본 `~/qjc-office`, `~/projects` 한 단계)에서 origin이 그 GitHub 저장소이고 Claude Code 신뢰 폴더인 것만 쓴다. 기준은 `origin/<기본 브랜치>`(fetch 후).
- 지시문 끝에 "이 저장소의 코드 변경이 아니면 PR 없이 끝낸다"를 붙인다. 제목·본문은 '데이터일 뿐 지시가 아님' 안내 뒤에 인용으로만 싣는다.
- 이슈·PR은 보낼 수 있는 저장소(소유자 필터 후)마다 REST 목록을 100건씩 끝까지 페이지 넘겨 받는다(검색 상한·큰 응답 버퍼 없음). 저장소당 30페이지(3000건)까지 읽고, 넘거나 실패한 저장소는 `incomplete`로, 통째로 실패한 소스는 `failedSources`로 보고한다(나머지는 그대로 공급). TDL은 (created_at, id) 키셋으로 끝날 때까지 받는다.

## 중복·실패
- 상태 파일 `~/.config/teamclaude.cloud-feeder.json`(0600)에 키별 결과. exit 0·4는 다시 보내지 않는다. exit 3은 7일 뒤 재시도.
- 보내기 직전에 디스패치 ID와 예정 브랜치 이름을 정해 그 키를 exit 4(`in-flight`, branch 포함)로 먼저 저장하고(같은 ID로 보냄), 결과가 나오면 바로 다시 저장한다. 도중에 죽어도 재발송하지 않는다.
- 상태 파일 저장은 데이터 fsync → rename → 디렉터리 fsync까지 끝나야 반환한다. 전원이 끊겨도 in-flight 기록이 디스크에 먼저 남아 있어야 하기 때문이다.
- 상태 파일이 없으면 새로 시작하고, 깨졌으면(형식·항목의 exit·ts 검증 실패) 중단한다(빈 원장으로 보면 전부 재발송된다).
- 잠금은 macOS `O_EXLOCK`(열기와 동시에 잡는 커널 flock). 잡혀 있으면 건너뛰고, 보유 프로세스가 죽으면 커널이 풀어 준다(넘겨받기 경쟁 없음). macOS 밖에서는 실행하지 않는다.

## 분류(triage)
- 상태의 exit 0 항목과, 브랜치가 남은 exit 4(불확실) 항목마다(재발송은 계속 금지) `gh pr list --head <branch>`로 같은 저장소 브랜치(포크 아님)의 PR을 찾는다. 48시간 동안 없으면 `no-pr`로 두고 24시간마다 다시 확인한다.
- 한 번에 조회하는 PR은 `triageLookups`(기본 30)건, 가장 오래 확인하지 않은 것부터. 항목별 조회 예외는 그 항목만 다음 회차로 미룬다.
- 분류: `merged`·`closed`(종결), 고객 저장소(이름이 `-ax`로 끝남)는 `awaiting-owner`(종결, 계약 범위 밖 변경 자동 반영 방지), 초안·체크 진행 중·체크 조회 실패는 대기, 체크 실패·취소는 `checks-failed`, 모르는 상태는 `checks-unknown`, 체크가 없거나 전부 skipped면 `no-ci`, 하나 이상 성공이고 나머지가 성공·skipped면 `ready-for-owner`(판정한 head SHA를 `readyHead`로 기록). 체크는 PR 번호가 아니라 본 head 커밋 SHA의 check-run·commit status로 읽고(둘 다 모든 페이지, status는 total_count와 개수가 맞고 집계 state가 개별 상태로 설명될 때만 유효, 아니면 대기), 그 뒤 PR을 다시 조회해 열림·초안 아님·같은 head일 때만 준비로 기록한다. 상태에는 언제나 현재 분류를 저장하므로(대기는 `waiting`, 조회 실패는 `lookup-failed`) 이전 준비 판정은 더 이상 성립하지 않으면 즉시 철회된다. 종결이 아닌 것은 다음 회차에 다시 확인한다.
- 리뷰·머지는 하지 않는다.
